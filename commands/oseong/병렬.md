# /oseong:병렬 — 병렬 작업 오케스트레이터

## 트리거
사용자가 `/oseong:병렬 [작업 설명]` 을 입력하면 즉시 아래 흐름을 실행한다.

---

## 실행 흐름

### STEP 1 — 작업 분석 및 판단

입력받은 작업을 분석해 다음을 결정한다:

1. **서브태스크 목록** 추출 — 작업을 최소 실행 단위로 쪼갠다
2. **의존성 그래프** 작성 — 어떤 태스크가 어떤 태스크 완료 후에 실행 가능한지
3. **병렬 가능 여부 판단**:
   - 독립 태스크가 2개 이상 동시 실행 가능 → **병렬 진행**
   - 모든 태스크가 직렬 의존 → **단일 진행**

판단 결과를 먼저 출력한다:
```
📋 작업 분석 결과

서브태스크:
  [A] ~~~ (독립)
  [B] ~~~ (독립)
  [C] ~~~ (A, B 완료 후 가능)

의존성:
  A ──┐
      ├──▶ C
  B ──┘

판단: 병렬 진행 (1차: A+B 동시 / 2차: C)
작업자 수: 2명 (A, B) → C는 결과 취합 후 이 인스턴스에서 진행
```

---

### STEP 2a — 단일 진행일 때

"단일 작업으로 진행합니다." 출력 후 이 인스턴스에서 바로 실행.

---

### STEP 2b — 병렬 진행일 때

#### 1) 지침서 파일 생성

`C:\Users\GKL\.claude\parallel-tasks\[작업명]-지침서.md` 에 저장:

```markdown
# [작업명] 병렬 작업 지침서

## 프로젝트 개요
[전체 맥락과 목적]

## 공유 정보
[모든 작업자가 알아야 할 공통 정보 — 레포명, DB 이름, 기술스택 등]

## 작업자별 담당
| 작업자 | 담당 | 산출물 |
|--------|------|--------|
| A | ... | ... |
| B | ... | ... |

## 의존성 규칙
- A, B는 독립 실행 가능
- C는 A, B 완료 후 실행

## 완료 기준
[각 작업자가 무엇을 완료해야 "끝"인지]

## 충돌 방지 규칙
[같은 파일/리소스를 건드리지 않도록 영역 분리 명시]
```

#### 2) 작업자별 프롬프트 출력

각 탭 제목으로 쓸 수 있게 **한 줄짜리 프롬프트**로 출력한다.
세부 내용은 지침서에 있으므로 프롬프트는 최대한 짧게.

**📤 아래 프롬프트를 각 인스턴스에 붙여넣으세요**

```
너는 작업자 A다. C:\Users\GKL\.claude\parallel-tasks\[작업명]-지침서.md 읽고 A 담당 작업 수행해라. 완료되면 "A 완료: [결과 요약]" 출력.
```

```
너는 작업자 B다. C:\Users\GKL\.claude\parallel-tasks\[작업명]-지침서.md 읽고 B 담당 작업 수행해라. 완료되면 "B 완료: [결과 요약]" 출력.
```

---

#### 3) 취합 대기

병렬 작업자들이 완료되면, 사용자가 결과를 이 인스턴스에 붙여넣는다.
그러면 의존 태스크(C 등)를 이 인스턴스에서 이어서 실행한다.

---

## 의존성 판단 원칙

병렬화 불가 케이스 (직렬로 처리):
- B가 A의 출력값(파일, ID, URL 등)을 입력으로 필요로 할 때
- 같은 파일을 동시에 수정해야 할 때
- 인증/환경변수가 한쪽에서 생성되고 다른 쪽에서 필요할 때

병렬화 가능 케이스:
- 완전히 다른 파일/서비스/레포를 다룰 때
- 공유 정보가 지침서에 미리 명시 가능할 때
- 각자의 산출물이 독립적일 때

---

## 공통 원칙
- 지침서는 반드시 파일로 저장 (`parallel-tasks/` 폴더)
- 작업자 프롬프트는 한 줄로, 코드블록으로 감싸서 출력
- 의존 태스크는 절대 병렬화하지 않는다
- 작업자 수는 독립 태스크 수와 동일하게 (불필요한 인스턴스 낙비 없이)
